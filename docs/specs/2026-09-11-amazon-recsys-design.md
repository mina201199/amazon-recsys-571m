## 1. 專案目標

> **給定使用者過去的互動歷史，預測他接下來會買哪些商品**，輸出排序過的 Top-10 清單。

這是 Amazon 首頁「為你推薦」在做的事，也是推薦系統最標準的 next-item prediction 任務。

**作品要證明的三件事：**
1. 能處理億級規模的資料，並說得出工程取捨的理由
2. 懂得正確評估——尤其時間切分與資料洩漏
3. 誠實報告結果，包含模型打不贏笨基線的情況

**刻意不做的（範圍控制）：**
- ❌ 深度學習推薦模型（無 GPU，時間不足）
- ❌ 評論文字的 NLP 處理（先把行為訊號做好）
- ❌ 線上 A/B 測試（沒有真實使用者）
- ❌ 完整 MLOps（主軸扣緊 ML，部署只做到能展示）

## 3. 關鍵發現：稀疏度迫使我們必須做全量

在 All_Beauty 類別（701,528 筆）上實測：

| 指標 | 數值 |
|---|---|
| 只有 1 筆評論的使用者 | **92.3%** |
| 少於 5 筆的使用者 | 99.7% |
| 平均每人筆數 | **1.11** |

**問題**：next-item prediction 需要使用者至少有 2 筆互動（一筆當輸入、一筆當答案）。
單一類別內，92.3% 的使用者無法使用。

**但全資料集平均是 571.54M ÷ 54.51M = 每人 10.5 筆。**
差距來自使用者的購買散落在不同類別。

> **結論：必須跨全部 33 個類別合併使用者歷史。單類別建模在方法上就是錯的。**
> 這讓「做全量」從「規模好看」變成「方法上的必要條件」。

## 5. 系統架構：兩階段召回與排序

無法對 4819 萬商品逐一打分，採用業界標準架構（YouTube、Pinterest 同構）：

```
使用者歷史 ──▶ ① 召回層 ──▶ 約 500 個候選 ──▶ ② 排序層 ──▶ Top-10
                (4819萬 → 500)                  (LightGBM)
```

### ① 召回層（Candidate Generation）

四路召回，結果合併去重：

| 路徑 | 做法 | 補捉什麼 |
|---|---|---|
| 熱門商品 | 近期互動數最高者 | 冷啟動保底 |
| **共現（co-visitation）** | 全量統計「買了 A 的人也買 B」 | 最強訊號，**吃全量資料的地方** |
| **ALS 矩陣分解** | 54.51M × 48.19M 稀疏矩陣（implicit 套件） | 潛在興趣 |
| 同類別熱門 | 使用者偏好類別中的熱門品 | 類別層級興趣 |

**評估指標：Recall@500** — 正確答案有沒有落在候選集內。
**這是整個系統的天花板**：召回沒撈到的商品，排序層再強也救不回來。
必須先把這個數字做高，再去調排序層。

### ② 排序層（Ranking）

LightGBM（LambdaRank）對 500 個候選精排。特徵分四組：

| 特徵組 | 內容 |
|---|---|
| 使用者 | 歷史互動數、平均給分、活躍時間跨度、偏好類別分布、常買價格帶 |
| 商品 | 近期熱度、平均評分、評分數、價格、類別、上架時長 |
| 使用者×商品 | ALS 分數、共現分數、類別匹配度、價格帶匹配度 |
| 時間 | 距上次互動天數、星期幾、月份 |

**負採樣策略**：負樣本必須取自「召回出來但使用者沒買」的商品，
不可從 4819 萬商品隨機抽。隨機抽到的商品太容易被排除，模型學不到有效區分能力；
用召回候選當負樣本，訓練分布才與線上推論一致。

## 6. 資料管線設計

### 6.1 核心洞察：訓練表其實很小

| 欄位 | 型別 | bytes |
|---|---|---|
| user_id（整數編碼） | int32 | 4 |
| parent_asin（整數編碼） | int32 | 4 |
| rating | int8 | 1 |
| timestamp | int32 | 4 |
| helpful_vote | int16 | 2 |
| verified_purchase | bool | 1 |
| category | int8 | 1 |
| | **合計** | **17** |

`571.54M × 17 bytes ≈ 9.7 GB` → Parquet + ZSTD 後約 **3–5 GB**。

**全量互動表可常駐 64 GB 記憶體**，特徵實驗迭代時間從數十分鐘降到秒級。

### 6.2 三個關鍵決策

**① 用 `parent_asin` 而非 `asin`**
同商品的顏色/尺寸變體共用 `parent_asin` 但有不同 `asin`。
用 `asin` 會虛增商品數、稀釋每個商品的互動訊號。
（All_Beauty 實測：115,709 asins → 112,565 parent_asins；服飾類差距會大得多。）

**② ID 必須整數編碼**
`user_id` 為 28 字元字串，571.54M 列光存 ID 就要 ~16 GB；
映射成 int32 後降到 2.3 GB。使用者 5451 萬、商品 4819 萬，均遠低於 int32 上限。

**③ 按「年」分區存放**
評估需按時間切分，年分區讓查詢只掃必要檔案。

### 6.3 工具選擇：DuckDB + Polars，不用 Spark

- DuckDB 負責 JSON 解析與大規模聚合（可超出記憶體，自動用滿 20 執行緒）
- Polars 負責特徵工程
- **不用 Spark 的理由**：壓縮後資料僅約 4 GB、單機記憶體 64 GB，
  引入分散式框架只增加複雜度而無效益

### 6.4 目錄結構

```
D:\amazon-reviews-2023\
├── raw\                    # 95.7 GB 原始 .jsonl.gz（轉檔後可刪）
├── parquet\
│   ├── interactions\       # 核心表，year=YYYY 分區，約 4 GB
│   ├── items\              # 商品屬性，約 3 GB
│   └── maps\               # user_id / item_id 整數映射表
└── features\               # 特徵快取
```

## 7. 時間切分與防洩漏

### 7.1 切分方案

| 用途 | 範圍 | 理由 |
|---|---|---|
| 統計與共現矩陣 | 全量（截至切分點） | 共現訊號需大量資料才穩定 |
| 模型訓練樣本 | 2018-01 ~ 2023-03 | 近期行為才有預測力 |
| 驗證集 | 2023-03 ~ 2023-06 | 調參用 |
| 測試集 | 2023-06 ~ 2023-09 | **只碰一次**，最終報告用 |

### 7.2 防洩漏檢查清單（將寫成自動化測試）

- [ ] 商品平均評分**只能**用切分點前的評分計算（用全期會包含未來資訊）
- [ ] 使用者統計特徵同上
- [ ] 切分必須按時間，**不可隨機切**
- [ ] 共現矩陣只能用訓練期資料建立
- [ ] 檢查測試集使用者是否污染了訓練特徵

> 資料洩漏是推薦系統最常見的致命錯誤，也是面試官最愛追問的點。

## 8. 評估設計

### 8.1 基線階梯（每階都要報數字）

1. 隨機推薦 — 地板
2. **全站最熱門商品** — 真正要打敗的對手
3. 共現召回 + 熱度排序
4. ALS
5. 多路召回 + LightGBM 精排 — 最終模型

> **若 5 打不贏 2，就照實寫出來並分析原因。**
> 熱門基線在推薦系統中經常出乎意料地強，誠實報告比灌水數字有價值。

### 8.2 指標

- `Recall@10`、`NDCG@10`
- `Recall@500`（召回層天花板，單獨報告）
- **Catalogue coverage**：模型總共推薦過多少種不同商品
  （只推 100 種商品的系統，recall 再高也是廢的）

### 8.3 分層評估

不只報總分，必須拆開：

- **冷啟動 vs 老使用者**（互動 <5 筆 vs ≥5 筆）— 由 §3 可知這是本資料集的主要痛點
- **熱門商品 vs 長尾商品** — 檢查模型是否只會推大熱門
